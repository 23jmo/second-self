## Problem Statement

Build a demo-winning hackathon project: a macOS "digital twin" that creates a second user session running simultaneously, controlled by an AI agent, visible to the primary user through a notch-resident UI. The demo loop is: someone walks up, types their name, the system profiles them, they give a command, and they watch their twin execute it live on a second macOS desktop.

## What Makes This Cool

The "it's me but it's not me" factor. You're watching a literal second desktop session that looks like your computer, controlled by AI, doing real work. Nobody has seen this before in a hackathon context. The combination of macOS Fast User Switching (a real second session, not a simulation) + AI computer use + real-time VNC viewing + instant profiling creates a cinematic experience that's genuinely novel.

The Codex second opinion suggested an "anticipatory twin" concept that we're incorporating into the core demo: when someone types their name, the second session wakes up already shaped around them (relevant tabs open, a draft task plan on screen) before they even give a command. This makes the twin feel alive, not just obedient. This is a core part of the demo, not a stretch goal.

## Constraints

- **Time:** ~24 hours (this weekend)
- **Platform:** macOS only (Fast User Switching is macOS-specific)
- **Team:** Solo builder
- **Hardware:** Single Mac running both sessions
- **Must work live:** Judges will watch it run. No pre-recorded demos.
- **Audience:** Hackathon judges who may or may not understand macOS internals

## Premises

All 5 are agreed but UNVERIFIED. Each must be proven before building on top of it.

1. macOS Fast User Switching can run a second session in background, accessible via VNC without manual GUI switching. **Known risk:** background sessions may have their WindowServer suspended, requiring a virtual display driver (e.g., BetterDisplay or a dummy HDMI plug) to keep the session rendering. Test this in Hour 0-1.
2. Dedalus Labs computer use API is reliable enough for a live demo (controls mouse, keyboard, reads screen).
3. A menubar/notch app with embedded VNC viewer and text input can be built in the time allotted.
4. Cookie cloning between macOS users is technically feasible. **CUT FOR MVP** — revisit only if core loop is solid by hour 16.
5. Tavily web search can build a meaningful stranger profile from just a name within a few seconds.

## Approaches Considered

### Approach A: Demo Spine First (CHOSEN)

De-risk VNC + Fast User Switching in hour 1-4. Build one hardcoded visual task. Layer Tavily profiling, then text input, then voice (if time permits). Notch UI is a simple menubar app, not a polished Dynamic Island clone. Natural fallback to "ghost desktop" (Approach C) if FUS fails by hour 4.

### Approach B: Cinematic Demo

Full identify → profile → anticipatory setup → command → watch loop with polished notch UI, embedded VNC viewer, and the "anticipatory twin" concept. Higher risk: any single component failure kills the demo. No fallback time.

### Approach C: Stage Magic

Skip Fast User Switching entirely. Run agent in a separate Space or VM. Use window capture or web-based screen share to show the agent working. The "second self" is a narrative device, not a literal second session. Most reliable but less technically impressive.

## Recommended Approach

**Approach A: Demo Spine First** — with a clear hour-by-hour build plan and explicit go/no-go gates for each layer.

### Build Order (Hour by Hour)

**PHASE 1: Prove the Plumbing (Hours 0-4)**

| Hour | Task | Go/No-Go |
|------|------|----------|
| 0-1 | Create second macOS user account (`sysadminctl`). Enable Fast User Switching. Verify second session starts in background. **Critical:** check if background session renders or if WindowServer is suspended. If suspended, install BetterDisplay or plug in a dummy HDMI adapter to force rendering. Grant TCC permissions (Privacy & Security → Screen Recording, Accessibility) for both users. | Can you `su` to the second user and run commands? Is the desktop rendering? |
| 1-2 | Enable VNC/Screen Sharing on the second user's session. Connect from primary session using `open vnc://localhost` or a VNC client library. | Can you SEE the second desktop live (not a frozen frame) from the first session? |
| 2-3 | Send commands TO the second session: run an AppleScript or `osascript` via `su -l seconduser`. Open Safari, navigate to a URL. Verify it appears in VNC view. | Can you CONTROL the second desktop remotely? |
| 3-4 | Test Dedalus Labs API: send a simple task ("open Safari and search for machine learning"). Verify it executes on the second session. | Does Dedalus reliably control the desktop? |

**GO/NO-GO GATE at Hour 4:**
- If VNC + FUS + Dedalus all work → continue to Phase 2
- If VNC + FUS work but Dedalus fails → replace Dedalus with PyAutoGUI/AppleScript for agent control
- If VNC fails → pivot to Approach C (ghost desktop with OBS/window capture)
- If FUS fails → pivot to Approach C

**PHASE 2: The Profiling Pipeline (Hours 4-8)**

| Hour | Task | Output |
|------|------|--------|
| 4-5 | Set up Tavily API. Build a Python script: input = name, output = structured profile (job title, company, interests, recent activity). Test with 5 real names. | `profile.py` that returns JSON |
| 5-6 | Build the "anticipatory twin" behavior (core, not stretch): given a profile, generate a list of 3-5 actions for the twin to take (open relevant websites, create a notes doc, set up workspace). Execute these via the computer use agent (Dedalus or its PyAutoGUI/AppleScript fallback) on the second session. | Twin desktop looks personalized within 10 seconds |
| 6-7 | Build the command interpreter: text input → parsed intent → task for the computer use agent. Start simple: "research [topic]", "draft an email about [subject]", "find information about [thing]". | User can type a natural language command and the twin executes it |
| 7-8 | Integration test: full loop. Name → profile → anticipatory setup → command → execution. Run it 5 times. Fix failures. | The demo loop works end-to-end |

**PHASE 3: The UI Shell (Hours 8-14)**

| Hour | Task | Output |
|------|------|--------|
| 8-10 | Build a macOS menubar app (Swift/SwiftUI). Place as a standard `NSStatusItem` menubar extra icon positioned to the right of the notch. States: idle indicator (green dot), click to expand `NSPopover` preview panel, button to show full VNC view in a separate `NSWindow`. | Working menubar app with 3 states |
| 10-12 | Embed VNC viewer in the full view. **Start with the reliable path:** open macOS Screen Sharing.app in a small borderless window positioned near the notch. This works immediately. **Only if time permits**, attempt noVNC in a `WKWebView` (requires `websockify` bridge to VNC port 5900, and note that `WKWebView` may block localhost WebSocket connections — may need `WKAppBoundDomains` or a custom `WKURLSchemeHandler`). | VNC feed visible via Screen Sharing.app (or embedded noVNC if time permits) |
| 12-13 | Add text input pill (Siri-style). `NSTextField` in a rounded pill shape, positioned below the notch area. Connects to the Python orchestrator via HTTP POST to `localhost:8420/command`. | User can type commands in the pill |
| 13-14 | Add voice input (stretch goal). Use macOS Speech Recognition framework (`SFSpeechRecognizer`). If time is tight, skip voice entirely and rely on text input. | Voice input triggers commands |

**PHASE 4: Polish and Rehearse (Hours 14-20)**

| Hour | Task | Output |
|------|------|--------|
| 14-16 | Run the full demo 10 times with different names. Log every failure. Fix the top 3 reliability issues. | Demo succeeds 8/10 times |
| 16-18 | Add demo rails: pre-loaded fallback profiles for common names, timeout handling (if Dedalus takes >15 seconds, show "thinking..." state), graceful error states. | Demo never visibly crashes |
| 18-20 | Rehearse the demo script. Time it (target: 2-3 minutes). Prepare talking points for judges: what's real, what's the vision, what's the tech. | You can run the demo cold with confidence |

**Hours 20-24: Buffer for debugging, sleep, and the unexpected.**

### Tech Stack (MVP only)

| Component | Technology | Why |
|-----------|-----------|-----|
| Menubar app | Swift + SwiftUI + AppKit | Native macOS, notch-aware, fast to build |
| VNC viewer | noVNC in WKWebView OR VNCKit | Embeddable, well-documented |
| Orchestrator | Python 3 | Fast prototyping, good library support |
| Computer use | Dedalus Labs API (fallback: PyAutoGUI + AppleScript) | Purpose-built for desktop control |
| Web profiling | Tavily API | Fast web search, returns structured data |
| Command parsing | Claude API (or any LLM) | Natural language → structured intent |
| Voice input | SFSpeechRecognizer (stretch) | Built into macOS, no dependencies |
| Session management | sysadminctl + su + launchctl | macOS system tools, no third-party deps |
| IPC (Swift ↔ Python) | Local HTTP server on port 8420 | Simple, debuggable, no framework needed |
| VNC WebSocket bridge | websockify (`pip install websockify`) | Required only if using noVNC in WKWebView |

## Open Questions

1. **Dedalus API access:** Do you have API credentials? What's the rate limit? Is there a sandbox/test mode? How does the Dedalus agent process get started in the second session, and does it communicate via HTTP API, stdin/stdout, or socket?
2. **macOS permissions:** Will the hackathon machine allow creating new user accounts? Does SIP need to be disabled for VNC between sessions? Is the machine MDM-managed (which may block `sysadminctl -addUser`)?
3. **TCC permissions:** Screen Recording, Accessibility, and Full Disk Access may need to be granted for both user accounts. These require GUI interaction in System Settings, so plan for manual setup time.
4. **Background session rendering:** Does the second user's WindowServer stay active when switched away? If not, you need BetterDisplay or a dummy HDMI adapter. Test this before anything else.
5. **VNC latency:** Is the VNC feed smooth enough to feel "live" or will there be visible lag that breaks the illusion?
6. **Tavily quality:** For uncommon names, does Tavily return useful results or noise?
7. **Demo machine:** Are you demoing on your personal Mac or a provided machine? (Affects setup time significantly)
